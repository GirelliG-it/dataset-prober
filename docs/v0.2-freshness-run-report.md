# Operational freshness checks and per-run report format 1

The profile agent's `check_freshness` now consumes immutable observations through
the reviewed [evaluator](v0.2-freshness-evaluation.md). Observation, collector,
evaluation-record and evaluation-policy versions are unchanged. This slice adds
versioned program claim selection and a separate per-run JSON report. It adds no
provider certification, interpretation rule, timezone assumption, adapter,
profile activation, history database, query service or scheduling.

## Grounding and selection

The model supplies exactly `source`, `dataset_id`, and `max_days_old`. Existing
argument validation precedes all operational effects; malformed calls create no
observation, evaluation or freshness-request record. Valid calls match fetched
candidates by exact source and dataset ID, without trimming or aliases. Missing
and ambiguous matches retain `candidate_not_inspected` and
`candidate_identity_ambiguous`.

At each fetch return (including handled fetch deadlines), the run captures the
original observation and a private association with the candidate, requested ID,
configured adapter/catalog, metadata endpoint and candidate retrieval URL. Checks
require that same captured association. They reject a replaced observation,
changed candidate resource, mismatched source/catalog, mismatched dataset ID, or
unexpected metadata endpoint. A CKAN returned name differing from the requested
ID is retained as evidence but does not establish an alias for evaluation.
Sanitized evidence IDs are never silently matched to differing raw IDs.

The expected CBS endpoint and TypedDataSet resource use the existing collector's
OData base and exact requested ID. CKAN's endpoint uses its existing configured
route and encoded requested ID. Known candidate retrieval URLs must match the
observation's safe URL identity, including its digest; redacted path text alone
does not establish resource equality. A failed/report-only candidate may lack a
retrieval URL: its original attached observation remains bound to that fetch,
without inventing a URL or discarding already collected resource provenance.
CKAN resource IDs remain those captured by the collector; the candidate summary
does not independently expose a second resource ID.

Only observation record format `1` and these explicit selection rules are used:

| Source | Selection version | Collector version | Selected field | Required semantics |
|---|---|---|---|---|
| CBS | `cbs-modified-selection-v1` | `cbs-tableinfos-freshness-v1` | `/value/0/Modified` | `UNVERIFIED` |
| CKAN | `ckan-modified-selection-v1` | `ckan-package-freshness-v1` | `/result/metadata_modified` | `CATALOG_METADATA_UPDATE` |

The selected claim must describe the observation's metadata endpoint and have the
collector's existing semantics. With claims present, a missing or duplicated
selected field is a grounding failure; another field is never substituted.
With no claims, the evaluator's explicit `None` reference path is used. Empty
claims on a failed or blocked collection retain that outcome's diagnostic.

Grounding diagnostics are `observation_missing`, `observation_not_captured`,
`observation_link_changed`, `observation_identity_mismatch`,
`observation_catalog_mismatch`, `observation_resource_mismatch`,
`observation_endpoint_mismatch`, `collector_not_supported`, `claim_not_found`,
`claim_identity_ambiguous`, `claim_scope_mismatch`, and `observation_id_conflict`,
in addition to the existing candidate-match reasons. They create request records
with null evaluation links, never invented observations or orphan evaluations.
The low-level executor accepts an optional run context for compatibility; without
one it cannot validate a previous fetch association and must return UNKNOWN.
The operational agent always supplies its run context.

## Evaluation and explanations

For each grounded check the agent creates a fresh evaluation UUID and captures
one UTC reference, then calls the pure evaluator with target `DATASET_CONTENT`,
the exact selected claim reference and the requested threshold. It passes no
interpretation rule. The model cannot choose claims, targets, timestamps or rules.
Repeated checks retain distinct evaluations even for the same observation and
threshold. Evaluation time is independent of collection time.

The tool response retains `passes: true/false/null` and high-level reason codes
`freshness_pass`, `freshness_fail` and `freshness_unknown`. It adds `verdict`,
`evaluation_reason`, `evaluation_id`, `observation_id`, `grounding_reason` and
`selection_rule_version`. Missing/ambiguous candidate reason codes are preserved.
The plain-language `reason` distinguishes collection failure, unusable timestamp,
timezone/precision limitations, temporal uncertainty and semantic inapplicability.
There is no fallback to `modified`, `last_updated` or display-day arithmetic.
Legacy `last_updated`/`days_old` result fields are no longer supplied. Exact ages,
precision, offset and interval boundaries remain in the full evaluation record.

**Current provider content verdicts are expected to be UNKNOWN.** A parseable CBS
Modified value has unverified semantics. A parseable CKAN package timestamp
describes catalog metadata, not dataset content. For example:

> Metadata was collected and its timestamp parsed, but this field describes
> catalog metadata; dataset-content freshness is unknown.

Missing zones, malformed values and other earlier limitations retain the
evaluator's diagnostic precedence, with semantic diagnostics still available in
the record. No collection, observation or interpretation is promoted to a
provider-certified content update. Synthetic applicable-content tests exercise
PASS and FAIL through a test-only selection rule; production rules are unchanged.

Freshness never mutates candidate status, assessment, loading eligibility,
consent or budgets. UNKNOWN is not an inspection failure, and PASS grants no
loading authority. Guarded collection and transactional loading are unchanged.

## Run retention and report

One `FreshnessRun` is created for the CLI run and shared across its sequential
profiles. Standalone `run_profile` calls create their own context when needed;
the returned `ProfileResult.freshness_run` exposes completed in-memory records.
No global mutable run state is used. Every captured observation is retained,
including failed/blocked attempts, evidence on handled deadlines, and observations
never evaluated. Identical observations are deduplicated; conflicting payloads
with the same observation ID are both retained, and checks on that ID are rejected.
Records are presented in capture/request/evaluation order, not sorted or inferred
from provider dates. Original observation IDs and payloads remain unchanged.

Each valid freshness request retains its one-based request number, requested
source, dataset ID and threshold, plus either an evaluation ID or a grounding
reason and explanation. Exact requested identities remain in memory. Serialized
identities and explanations use existing URL-text sanitization; `identity_sanitized`
records whether an identity changed. Canonical observation and evaluation payloads
are serialized explicitly without a further presentation transformation.

Completed records survive the existing handled model/fetch timeouts, budget stops,
normal/end-of-output conversation termination, and subsequent malformed tool
requests. Completed-call usage and earlier candidates are retained. Unrelated
programming exceptions are not suppressed or converted into success.

The resolved output directory receives `freshness-<run-UUID>.json` when any
observation, evaluation or request diagnostic exists. The report contains:

- `report_format_version: "1"` and `run_id`.
- `observations`: complete original observation records.
- `evaluations`: complete unchanged evaluator records, including their embedded
  observations and exact integer time information.
- `requests`: request-to-evaluation links or explicit grounding diagnostics,
  explanatory text and selection-rule versions.

The filename is run-specific and opened exclusively: existing files are refused,
not replaced, renamed or retried under a different UUID. The directory is created
only immediately before an artifact write. Help, profile listing and disabled
profile invocations never create a run/output directory or write a report.

`agent_results.json` remains the existing candidate summary with the same schema,
filename and replacement behavior. Summary and freshness-report writes are
attempted independently, including a diagnostics-only run with no candidates.
Both use explicit serialization and strict JSON with no `default=str`. Encoder
`TypeError`/`ValueError` and file/directory `OSError` failures are reported narrowly;
record-construction/programming errors are not hidden. Any handled write/encoding
failure produces CLI status **2**, while a successful completed run returns **0**.
Neither failure clears completed in-memory records or changes evaluation outcomes.

This is a **run report**, not durable queryable history. Writes are not a
transaction across the two artifacts. An interrupted/failed write can leave an
incomplete file, and an existing report path will remain protected from overwrite.
There is no automatic reconciliation or retry, guaranteed retention after failed
writes/process exit, atomic publication, or crash/power-loss recovery claim.
Monitoring comparisons and storage-v1 are unchanged.

## Offline validation

`tests/unit/test_freshness_run.py` covers grounded CBS/CKAN fetch-to-report flows,
semantic UNKNOWN explanations, synthetic PASS/FAIL without loading authority,
repeat checks, mismatched identities and claim scope, failed/blocked/absent claims,
malformed calls, retained model-call usage on handled stops, diagnostics-only runs,
write independence, collisions, serialization failures and read-only CLI paths.
The existing metadata-deadline CLI regression additionally checks the new report
preserves the original observation and contains no invented evaluations. Existing
evaluator, observation, budget, validation and loading tests remain in force.
