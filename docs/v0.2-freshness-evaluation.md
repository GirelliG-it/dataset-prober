# Standalone freshness evaluator — policy elapsed-freshness-v1

`dataset_prober.freshness_evaluation.evaluate_freshness` is a pure, opt-in Python
API over immutable [freshness observations](v0.2-freshness-evidence.md). The agent
now calls it through [grounded checks and per-run reports](v0.2-freshness-run-report.md).
The pure evaluator's policy and record formats are unchanged. Agent tool inputs,
adapters, candidate serialization, loading authorization, monitoring comparisons
and storage-v1 are unchanged. No evaluator result authorizes loading. The evaluator
itself performs no I/O, and no real provider interpretation rule is supplied or
certified. There is no history service or crash/power-loss recovery claim.

## Inputs and identity

The caller supplies an observation, a `ClaimReference(observation_id, index)`, a
UUID object for the evaluation ID, a standard `datetime` with `tzinfo is UTC` and
`fold == 0` for `evaluated_at`, and an integer `max_days_old >= 0`. Booleans are
rejected. Naive/local, custom-zone and datetime-subclass references are rejected,
not converted implicitly. The caller captures/converts its reference explicitly.

The claim reference must name the supplied observation and an existing zero-based
claim index. The original claim order, metadata resource and field path remain in
the embedded observation. No fallback claim is selected. `None` explicitly denotes
absence and is accepted only when the observation has no claims. For an ABSENT,
NULL or WRONG_TYPE field, select that claim normally. Invalid references, invalid
caller parameters and mismatched rules raise `ValueError`; provider-data problems
produce records with UNKNOWN instead. No broad exception handler conceals defects.

The target defaults to `DATASET_CONTENT`. Only `DATASET_CONTENT_UPDATE` semantics
can establish its PASS or FAIL. Explicit `CATALOG_METADATA` requires
`CATALOG_METADATA_UPDATE`. Neither metadata updates nor UNVERIFIED semantics can
establish fresh **or stale** dataset content. There is no metadata-age fallback.
Current CBS and CKAN annotations are unchanged and are not certified content claims.

Evaluation neither reads a clock nor generates an ID. Identical inputs produce
identical records. An intentional new evaluation receives a new UUID from its
caller; reusing inputs and an ID reproduces the same evaluation. UUID allocation,
global uniqueness enforcement and durable save retries remain outside this policy.

## Exact time policy

A day means **86,400 elapsed seconds**. All normalized values and ages are integer
100-nanosecond ticks. The UTC origin is `1970-01-01T00:00:00Z`, using the proleptic
Gregorian calendar without leap-second arithmetic. Negative ticks are supported.
Reference microseconds multiply by ten exactly; no floating-point timestamps,
rounding or truncation are used. Collection `observed_at` remains provenance only.
Every age and future comparison uses the single supplied `evaluated_at`.

Let `R` be that reference, `D` the threshold in ticks and `C = R - D` the cutoff.
For an exact instant `t`:

- PASS if `C <= t <= R`, including both boundaries.
- FAIL if `t < C`.
- UNKNOWN (`future_timestamp`) if `t > R`. There is no skew allowance.

The complete accepted timestamp grammar is
`YYYY-MM-DDTHH:MM:SS[.fraction][Z|±HH:MM]`. ASCII digits and uppercase `T`/`Z` are
required. Missing zones are recognized but require an explicit rule to interpret.
The entire value must match: no whitespace, suffixes, valid-prefix parsing, repairs
or trimming. Calendar years 0001–9999 and valid calendar/time components are
required; hour 24 is invalid. Numeric offset hours must be 00–23 and minutes 00–59.
The supplied offset spelling (including `Z` versus `+00:00`) is retained separately.

Fractions of one through seven digits are exact. Their original digit count is
retained even for trailing zeros. More than seven digits yield
`unsupported_precision` and no normalized value. Second 60 yields
`unsupported_leap_second`; it is never normalized to the next minute. Calendar
and offset component errors take precedence over these unsupported forms.

`-00:00` means an unknown offset (`timezone_unknown_offset`), including when a
rule is supplied; it is not silently reinterpreted as UTC. A missing timezone
without an applicable rule gives `timezone_missing`.

## Provider rules and coarse precision

`InterpretationRule` is immutable and carries an ID, version, exact source,
catalog identity, metadata resource and field path. All scope fields must match
the selected claim. It supplies exactly one of:

- A fixed offset in integer minutes, from -1439 to 1439. The rule asserts this
  fixed offset applies to the selected provider field, including both boundaries
  of any date interval. Its use is recorded as `timezone_assumption`.
- A named zone, recorded for provenance but **not interpreted in this version**.
  Missing-zone instants and dates then yield `named_timezone_unsupported`, with
  no normalized value or applied assumption. This includes ambiguous local times
  and gaps; neither DST folds nor gaps are guessed. No timezone database is read.

Explicit known offsets in provider timestamps take precedence over a supplied
rule. The supplied rule is still recorded, but `timezone_assumption` is null when
it was not used. No country, profile, laptop or server timezone is consulted.

A date-only `YYYY-MM-DD` preserves DAY precision. With a reviewed fixed-offset
rule it denotes **[local day start, next local day start)**. Both boundaries are
converted to UTC before comparison. No exact provider midnight timestamp is
invented. This implementation cannot interpret named-zone days; it does not
assume that DST local days last 24 hours. Without a rule the result is
`timezone_missing`, retaining DAY precision and no interval.

For a normalized interval `[S, E)`:

- PASS only if `S >= C` and `E <= R`: every possible instant is in the window.
- FAIL only if `E <= C`: the exclusive end means every possible instant is older
  than the inclusive cutoff, even when `E == C`.
- If `S > R`, UNKNOWN with `future_timestamp`.
- Otherwise, if `E > R`, UNKNOWN with `interval_future_overlap`, including an
  interval beginning exactly at `R`.
- Otherwise, UNKNOWN with `interval_crosses_cutoff`.

The age bounds are `(R - E, R - S]`; the lower bound is exclusive and the upper
bound inclusive. Exact-instant age has equal inclusive lower and upper bounds.
At `2026-10-22T12:00:00Z`, UTC date `2026-10-20` has ages `(36h, 60h]`: a one-day
limit FAILs, a two-day limit is UNKNOWN, and a three-day limit PASSes.

Year-only `YYYY` retains YEAR precision and yields `insufficient_precision`, even
with a rule. Year zero is invalid. Unsupported syntax has no inferred precision;
recognized but invalid calendar forms retain their syntactic precision.

## Diagnostics and precedence

Parsing and age calculation are independent of collection status, sanitization
and meaning. A valid interpretation is retained even when it cannot support the
target. Sanitized evidence can never establish PASS or FAIL. The full immutable
observation preserves its sanitization flag, provider claims, presence/type,
collector version and collection reason.

Supporting diagnostics are ordered as follows; the first is the primary reason
and any diagnostic makes the verdict UNKNOWN:

1. `collection_failed` or `collection_blocked`.
2. `timestamp_absent`, `timestamp_null` or `timestamp_wrong_type`.
3. `sanitized_evidence`.
4. Parsing/interpretation failure: `invalid_timestamp`,
   `unsupported_leap_second`, `unsupported_precision`, `insufficient_precision`,
   `timezone_unknown_offset`, `timezone_missing` or `named_timezone_unsupported`.
5. Temporal uncertainty: `future_timestamp`, `interval_future_overlap` or
   `interval_crosses_cutoff`.
6. `semantics_not_applicable`.

Within parsing, full grammar/calendar/offset validation precedes leap-second,
fractional-precision and timezone handling, in that order. Parsing returns one
diagnostic at its first unsupported boundary; it does not claim to diagnose all
possible problems after interpretation has stopped. Semantic applicability is
still checked independently. With no limitations, the primary reason is
`freshness_pass` or `freshness_fail` and the diagnostic tuple is empty.

Parsing status is `PARSED`, `INVALID`, `UNSUPPORTED`, `UNRESOLVED` (timezone), or
`NO_EVIDENCE` (presence/type). Collection status, parsing status and freshness
verdict remain distinct. No storage outcome is fabricated in this slice.

## Immutable record and explicit serialization

`FreshnessEvaluation` contains the caller UUID, record version `1`, policy version
`elapsed-freshness-v1`, original immutable observation, exact claim reference or
absence, UTC evaluation reference, target, threshold, optional immutable rule,
interpretation, exact age bounds, verdict, primary reason and diagnostic tuple.
Nested records contain immutable scalar values. The full observation provides
the observation ID, exact subject identities, original evidence, observed time,
observation record version and collector version. Rule version, evaluation record
version and policy version are separate. A later policy can evaluate that same
observation without altering this decision.

`to_dict()` explicitly returns detached JSON values, including normalized unit,
UTC origin, instant/interval kind and boundary flags. It does not stringify unknown
objects, allocate IDs or read clocks. All seven provider fractional digits remain
in both evidence and integer interpretation. Consumers must preserve integer
precision: JavaScript floating-point numbers cannot represent every tick exactly.
No JSON import or storage schema is added here.

## Offline acceptance

`tests/unit/test_freshness_evaluation.py` uses synthetic content claims and fixed
references. It covers one-tick cutoff/zero-threshold boundaries, offset
equivalence, all supported fractional lengths, exact reference microseconds,
coarse intervals and exclusive ends, invalid values, missing/unknown zones,
unresolved named-zone gaps/folds, collection/presence distinctions, sanitization,
semantic applicability, claim selection, scoped rules, repeatability, nested
immutability, detached serialization and process-timezone independence. Existing
evidence, validation, budget and loading suites continue to protect their existing
boundaries. Operational integration tests separately verify grounding, expected
UNKNOWN content outcomes for current providers, and per-run report retention.
