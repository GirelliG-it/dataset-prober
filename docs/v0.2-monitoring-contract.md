# v0.2 monitoring comparison contract

The monitoring implementation defines immutable observations and a pure comparison function in `dataset_prober.monitoring`, plus a standalone DuckDB store in `dataset_prober.monitoring_store`. The store accepts an explicit path and existing observations; it does not collect observations, expose a CLI, or contact CBS. Source registration, ID generation, default-path integration, and runtime caller wiring remain future work. The package release version remains unchanged until release work.

## Agreed behavior

- A failed or blocked attempt returns UNKNOWN. Keep it in the eventual observation history; it does not replace the successful baseline.
- Select the latest strictly earlier successful observation for the same source, contract version, and checker version. Tied baseline timestamps are ambiguous.
- Compare evidence only when kind, resource, and normalization rule version match. A catalog response and a dataset response are different resources.
- Missing evidence has an explicit reason: NOT_PROVIDED, NOT_CHECKED, INVALID, or CHECK_FAILED. Never treat missing values as matching evidence.
- First usable change evidence establishes BASELINE. A first observation without usable evidence returns UNKNOWN.
- Changed comparable revision, modification, ETag, or schema evidence returns POSSIBLY_UPDATED. This reports a signal, not proof of a dataset content change.
- Matching signals return NO_CHANGE_DETECTED only when no available signal on either side was lost or incomparable. This is not a freshness guarantee.
- A title change is recorded in the evidence comparison but cannot alone determine dataset change.

Conservative choice: an unchanged revision alongside a disappearing timestamp returns UNKNOWN; a changed comparable revision still supports POSSIBLY_UPDATED. Later provider-specific precedence rules may refine this, with an explicit comparison version change.

## Example

Monday succeeds, Tuesday times out, Wednesday succeeds: Wednesday compares against Monday. Tuesday remains operational evidence. Identical Monday/Wednesday metadata cannot rule out an intervening change that was reverted.

## Collector responsibilities and next slice

The comparison model consumes validated strings; it does not establish provider semantics. Collectors must preserve timestamp precision, distinguish provider evidence from assumptions, sanitize stored resource identifiers and failure reasons, and version normalization/fingerprint rules. Supply the same explicit evidence slots on each check, including absence reasons.

Before the CBS collector is implemented, select a registered table and verify the meaning of its provider metadata. Its existing fetch operation retrieves samples and should not be reused for a metadata-only check. Keep sample retrieval, full content hashing, ingestion, scheduling, and agent investigation outside this slice.

The existing authorization-bound candidate identity remains separate from persistent monitoring identity. Comparison results never authorize ingestion.

The deterministic test suite covers recovery, missing evidence, endpoint and rule changes, metadata-only changes, and ambiguous baselines. No live provider claims have been validated in this slice.

## Persistence contract — standalone store

The requirements below are implemented by the standalone store and covered by
offline tests in `tests/unit/test_monitoring_store.py`. Runtime monitoring callers
are not wired to the store. The CBS experiment's saved report is not a monitoring
persistence contract.

For the same current observation and historical observations supported by the
storage format, saving and reloading must preserve baseline selection and the
complete `Comparison` when evaluated by the same comparison implementation and
version. This guarantee includes the comparison reason and ordered evidence.

### Stored observations and format v1 timestamps

- Retain `SUCCEEDED`, `FAILED`, and `BLOCKED` observations.
- Preserve every `Observation` field: `observation_id`, `source_id`, `checked_at`,
  `check_status`, `evidence`, `failure_reason`, `contract_version`, and
  `checker_version`.
- Preserve each evidence item's `kind`, `resource`, `rule_version`,
  `availability`, and `value`, including null values and evidence order. Provider
  modification timestamps remain verbatim evidence strings, with their original
  precision and timezone notation; the UTC restriction below concerns only
  `checked_at`.
- Accept only observations whose JSON encode/decode round trip preserves the
  original observation's field values and evidence order exactly. Reject a
  differing round trip with a storage error before inserting, leaving existing
  history unchanged. In particular, the Python string `"\ud83d\ude00"` is
  unsupported because JSON decoding combines its two surrogate code points into
  `"\U0001f600"`; the latter, single-code-point representation is supported.
  Do not normalize the supplied observation to make it storable.
- Storage format v1 accepts standard Python `datetime` values with
  `tzinfo is datetime.UTC` (also named `datetime.timezone.utc`) and `fold == 0`.
  Encode `checked_at` as `YYYY-MM-DDTHH:MM:SS.ffffff+00:00`, preserving all six
  microsecond digits, including zeros. Decode to the same UTC representation.
- Explicitly reject unsupported timestamp representations with a storage error
  before appending: naive datetimes, nonzero fixed offsets, named zones
  (including `ZoneInfo("UTC")`), custom timezone objects, datetime subclasses,
  and `fold == 1`. A zero offset at one instant is not sufficient for acceptance.
  Do not convert unsupported values to UTC during storage. Reject stored
  timestamps that do not conform to the v1 encoding rather than normalizing them.
- Use explicit storage-format version `1`, separate from contract, checker, and
  comparison versions. Reload validated `Observation` and `Evidence` objects.
  Invalid records, missing required stored fields, and unsupported storage-format
  versions must raise an explicit storage error. Do not silently skip records,
  repair them, supply model defaults for omitted fields, or substitute empty
  history. A failed history read must not supply a partial history for comparison.

These storage restrictions do not narrow the in-memory observation model or
change comparison semantics. Currently, `Observation.__post_init__` requires an
aware datetime but does not normalize it. `compare_observation` uses Python's
datetime `<`, `max`, and `==` directly. The only runtime caller, the CBS
experiment, defaults to `datetime.now(UTC)` and passes its injected clock's value
through unchanged. Its offline clock and the monitoring test helper also use
UTC. The comparison suite additionally exercises a fixed `+02:00` offset; that
in-memory behavior remains supported, but its timestamp is outside storage v1.

### Append behavior and storage outcomes

- History is append-only through the monitoring store. A new observation must
  not modify or replace earlier observations.
- `observation_id` is unique within the store. Reject every duplicate ID,
  including an identical payload, with an explicit storage error and leave the
  existing observation unchanged. Retain the same ID when reconciling a save
  attempt; do not create a new identity merely to retry storage.
- Store each complete observation atomically, including all evidence. A rolled
  back transaction must leave no partial observation or change earlier history.
  Surface write and commit errors explicitly.
- Define **successfully saved** as an acknowledged transaction commit whose
  complete observation remains available after normal close/reopen. A buffered
  value or an uncommitted insert is not a successful save.
- Keep storage outcomes separate from monitoring outcomes. A successful check
  does not imply successful storage. A storage error must not rewrite
  `check_status`, `failure_reason`, or the comparison result.
- If execution is interrupted before save confirmation, reconcile by
  `observation_id` after reopening. A complete matching observation confirms its
  presence; absence allows a retry with the same ID; a different payload is a
  conflict. A failed lookup does not establish absence. Missing confirmation
  alone does not establish whether the transaction committed.

The initial durability acceptance tests establish retention across normal
close/reopen and explicit rollback of injected transaction failures. They do not
establish abrupt-process termination or power-loss recovery. Those recovery
claims require separate acceptance tests; normal restart tests alone must not be
reported as verifying them.

### Comparison after reload

Pass reloaded observations to `compare_observation`; do not implement a separate
baseline policy in storage. Only strictly earlier `SUCCEEDED` observations with
a different observation ID and matching source, contract version, and checker
version qualify. Failed and blocked attempts remain in history but cannot become
baselines. Ties at the latest eligible timestamp remain ambiguous; insertion or
retrieval order must not break them.

The latest eligible successful observation remains the baseline even when its
evidence is missing. Do not fall back to an older, richer observation. No usable
comparable change evidence produces `UNKNOWN`; partial evidence follows the
existing rules, including `POSSIBLY_UPDATED` when another comparable signal
changed. Evidence is compared only when kind, resource, and rule version match
and both values are `PRESENT`. Saving history never authorizes ingestion.

### Offline acceptance scenarios

All persistence scenarios use temporary local storage and synthetic observations.
The store suite covers these scenarios, including an injected loss of commit
acknowledgement followed by reconciliation. That injection is not a process-crash
or power-loss test.

1. **Restart and recovery from a failed check:** save Monday's successful
   observation and close the store. Reopen, save Tuesday's `FAILED` observation
   with `failure_reason="timeout"`, and close. Reopen, save Wednesday's successful
   observation, then close and reopen again so Wednesday is also reloaded. Assert
   all fields of all three observations are preserved. Compare reloaded Wednesday
   against reloaded Monday and Tuesday: Monday is the baseline, Tuesday remains
   in history, and the complete result equals the in-memory result. Identical
   usable Monday/Wednesday evidence yields `NO_CHANGE_DETECTED`. Also cover a
   retained `BLOCKED` observation that cannot replace Monday.
2. **Duplicate IDs:** attempt both an identical and a conflicting duplicate.
   Each raises a storage error; reopening shows exactly the original observation
   and unchanged earlier history.
3. **Rollback:** inject a failure after the write starts but before commit.
   Require an explicit storage error. Reopening shows no part of the attempted
   observation and preserves all earlier observations. A successful check's
   in-memory status and failure reason remain unchanged by the storage failure.
4. **Timestamp equality, ordering, and eligibility:** round-trip UTC observations
   with equal timestamps and timestamps one microsecond apart, including across
   a second/day boundary. Assert unchanged microseconds and pairwise `==`, `<`,
   and `>` results. For the same current/history inputs, assert identical complete
   comparisons: strictly earlier timestamps qualify, equal/current and future
   timestamps do not, and tied latest eligible observations produce `UNKNOWN`
   with no selected baseline. Repeat with shuffled history retrieval order.
5. **Unsupported timestamps:** reject non-UTC fixed offsets, naive values,
   custom timezone representations, datetime subclasses, and UTC values with
   `fold == 1`. Explicitly reject named-zone observations, including
   `ZoneInfo("UTC")` and `Europe/Amsterdam` timestamps around spring-forward and
   fall-back transitions (both folds of the repeated hour). No rejected append
   alters history. A stored nonconforming timestamp also raises a storage error.
6. **Compatibility and missing evidence:** after reload, other sources and
   incompatible contract/checker versions remain excluded. The latest eligible
   successful observation with no evidence remains the baseline and produces
   `UNKNOWN`. Preserve kind/resource/rule-version evidence incompatibility,
   unavailable evidence, and partial-evidence outcomes. Compare complete results
   against the corresponding in-memory results.
7. **Invalid stored records:** separately introduce invalid observation fields
   (for example, a missing source ID or a failed status without a reason) and
   invalid evidence fields (for example, `PRESENT` with a null value or duplicate
   evidence keys). Include valid records alongside each invalid record. Loading
   history must raise an explicit storage error, without silently skipping or
   repairing the record, returning only valid records, or substituting empty
   history. The read must not modify stored data.
8. **Unsupported format:** open/read a store or record declaring an unsupported
   storage-format version, including a mixed history with supported records.
   Require an explicit storage error rather than silently skipping, migrating,
   repairing, or substituting empty history. Preserve stored data unchanged.

### Standalone interface and remaining integration

`MonitoringStore(path)` opens an explicit filesystem path using the existing
DuckDB dependency. Its parent directory must already exist. A new or empty
database is initialized transactionally; an existing incompatible database raises
`MonitoringStorageError` rather than being reinitialized. The store is independent
of the authorized dataset-loading wrapper and is intended for one caller/writer
at a time; instances are not thread-safe.

- `append(observation) -> None` commits one supplied `Observation`. A normal
  return acknowledges commit. `DuplicateObservationError`, a subclass of
  `MonitoringStorageError`, reports a confirmed already stored ID. Other
  constraint failures raise an ordinary `MonitoringStorageError` and leave
  history unchanged.
- `history() -> tuple[Observation, ...]` returns a complete validated snapshot
  across all sources and statuses, ordered by observation ID using Python Unicode
  code-point ordering. It does not select baselines. The tuple is materialized
  before return, so invalid records cannot expose a partial result.
- `close()` is idempotent. Context-manager exit closes the connection, including
  after caller exceptions; it does not undo appends that already committed.
  Operations on a closed store raise `MonitoringStorageError`.

The `monitoring_format` table contains exactly one integer format version.
`monitoring_observations` contains an observation ID primary key, an integer
storage-format version per record, and the complete JSON payload in a `VARCHAR`.
Payloads include all model fields, with evidence stored as an ordered array.
Duplicate JSON keys, unknown or missing fields, and noncanonical timestamps are
invalid. History reads validate both the store version and every record version.

Callers can reconcile an uncertain save by finding its ID in the complete
`history()` result; a dedicated lookup method is deferred. Source registration,
ID generation, default-path integration, and runtime wiring remain future tasks.
The experiment's `attempt-1`/`attempt-2` IDs cannot serve as store-wide identities
across runs. No crash or power-loss recovery claim is established by this suite.
