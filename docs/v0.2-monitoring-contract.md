# v0.2 monitoring comparison contract

This first implementation slice defines immutable observations and a pure comparison function in `dataset_prober.monitoring`. It does not yet collect or persist observations, expose a CLI, or contact CBS. The package release version remains unchanged until release work.

## Agreed behavior

- A failed or blocked attempt returns UNKNOWN. Keep it in the eventual observation history; it does not replace the successful baseline.
- Select the latest strictly earlier successful observation for the same source, contract version, and checker version. Tied baseline timestamps are ambiguous.
- Compare evidence only when kind, resource, and normalization rule version match. A catalog response and a dataset response are different resources.
- Missing evidence has an explicit reason: NOT_PROVIDED, NOT_CHECKED, INVALID, or CHECK_FAILED. Never treat missing values as matching evidence.
- First usable change evidence establishes BASELINE. A first observation without usable evidence returns UNKNOWN.
- Changed comparable revision, modification, ETag, or schema evidence returns POSSIBLY_UPDATED. This reports a signal, not proof of a dataset content change.
- Matching signals return NO_CHANGE_DETECTED only when no available signal on either side was lost or incomparable. This is not a freshness guarantee.
- A title change is recorded in the evidence comparison but cannot alone determine dataset change.

Conservative choice: an unchanged revision alongside a disappearing timestamp returns UNKNOWN; a changed comparable revision still supports POSSIBLY_UPDATED. Later provider-specific precedence rules may refine this, with an explicit comparison version change.

## Example

Monday succeeds, Tuesday times out, Wednesday succeeds: Wednesday compares against Monday. Tuesday remains operational evidence. Identical Monday/Wednesday metadata cannot rule out an intervening change that was reverted.

## Collector responsibilities and next slice

The comparison model consumes validated strings; it does not establish provider semantics. Collectors must preserve timestamp precision, distinguish provider evidence from assumptions, sanitize stored resource identifiers and failure reasons, and version normalization/fingerprint rules. Supply the same explicit evidence slots on each check, including absence reasons.

Before the CBS collector is implemented, select a registered table and verify the meaning of its provider metadata. Its existing fetch operation retrieves samples and should not be reused for a metadata-only check. Keep sample retrieval, full content hashing, ingestion, scheduling, and agent investigation outside this slice.

Persistence will need a stable source registry, append-only observation history, unique observation IDs, transaction handling, and a serialization contract. The existing authorization-bound candidate identity remains separate from persistent monitoring identity. Comparison results never authorize ingestion.

The deterministic test suite covers recovery, missing evidence, endpoint and rule changes, metadata-only changes, and ambiguous baselines. No live provider claims have been validated in this slice.
