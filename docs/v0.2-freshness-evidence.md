# Freshness evidence in fetched candidate results

This defines the immutable observation capture slice of the v0.2 design.
The [pure evaluator](v0.2-freshness-evaluation.md) now consumes these observations
through [agent checks and per-run reports](v0.2-freshness-run-report.md), without
changing their record format or capture semantics. Legacy `modified` summaries
and helper methods remain unchanged, including their truncation, prefix-parsing
and future-date limitations; operational `check_freshness` no longer uses them.
The monitoring comparison model and storage-v1 contract are unchanged.

## Record format 1

`DatasetResult.freshness_observation` is optional and defaults to `None`. It is
the final constructor field, so existing positional arguments retain their
positions. `to_dict()` adds `freshness_observation`, either null or an explicit
JSON object. Other serialized fields keep their existing meaning and values.
The existing agent candidate JSON therefore includes captured evidence; it is
still a candidate summary that can be overwritten. The separate run report
retains observations and evaluations under a new UUID filename, not a history service.

The frozen `FreshnessObservation` contains:

- A UUID4 observation ID, record version `1`, and collector rule version
  (`cbs-tableinfos-freshness-v1` or `ckan-package-freshness-v1`). Each new fetch
  attempt receives a new ID. Serialization neither generates an ID nor reads a clock.
- Source, existing configured adapter/catalog identity, dataset ID, and selected
  resource ID and URL identity where known. CKAN retains the selected package
  identifier and resource ID without trimming or coercion. The metadata endpoint
  records the requested package identity, which can differ from its returned name.
  Unknown CKAN resource identity is null, not invented. CBS's table and
  TypedDataSet target are known from the request.
- Safe metadata endpoint identity, including logical request parameters.
  Existing `safe_url_identity` and `sanitize_url_text` mechanisms redact URL
  credentials, query values and fragments. Sensitive URL identities retain their
  digest, so identical redacted paths do not merge different requests/resources.
  These are diagnostic identities, not new ingestion authorizations or durable
  rename/alias mappings.
- `observed_at`, captured once at metadata completion or failure, using a
  standard UTC datetime. JSON uses six microsecond digits and `+00:00`.
  Adapter-level `utc_now` functions provide a replaceable clock seam for tests.
- `collection_status`: `SUCCEEDED`, `FAILED` or `BLOCKED`, independent of
  candidate inspection status and timestamp usability. Unsuccessful attempts
  include a machine-readable `reason_code` and no invented provider claims.
- An immutable tuple of timestamp claims.

Each frozen claim separates the provider value from the collector's annotations:
metadata resource, exact JSON field path, presence, semantics and sanitization
flag. Presence is `ABSENT`, `NULL`, `WRONG_TYPE` or `STRING`; an empty or malformed
string is still a provider string, not a date interpretation. Absent and explicit
null values both serialize as null but retain distinct presence values.

Retained values use immutable JSON text internally, including nested wrong-type
objects and arrays. Serialization returns a fresh JSON value. Mutating the
original provider payload or a serialized copy cannot change the observation.
There is no `default=str` fallback: non-JSON values, nonfinite numbers and lossy
JSON representations are rejected. Ordinary timestamp strings retain every
fractional digit and their timezone notation. URL-shaped strings, including
those inside wrong-type objects and keys, follow existing sanitization rules;
`sanitized: true` records any resulting value change. Such values are not claimed
to be verbatim unsanitized evidence.

If distinct object keys collide after sanitization, capture raises `ValueError`
and rejects the entire claim, including collisions in nested objects or arrays.
It never renames keys, drops members or chooses a winning value. The diagnostic
contains no provider keys or values, and the original payload remains unchanged.
Existing adapter failure handling returns a failed, non-loadable candidate with
a `FAILED` observation, reason `metadata_collection_failed` and no claims.

## Capture boundaries and meaning

CBS fetch captures `/value/0/Modified` as `UNVERIFIED` and
`/value/0/MetaDataModified` as `CATALOG_METADATA_UPDATE`, from the requested
TableInfos metadata resource. CKAN fetch captures `/result/metadata_modified`
as `CATALOG_METADATA_UPDATE` from package_show, separately from its selected CSV
resource. It does not substitute a resource's `last_modified` for the package
field. The resource-selection rule is unchanged.

These are collector annotations based on field roles, not live certification of
provider semantics. `DATASET_CONTENT_UPDATE` is representable, but neither
collector assigns it in this slice. Metadata changes do not establish content
freshness, and no timestamp interpretation or verdict is added to these records.

Capture precedes legacy date-display conversion and sample retrieval/inspection.
Successfully collected metadata stays attached even if these later operations
return a failed or report-only candidate. In particular, wrong-type timestamps
that already fail legacy conversion continue to produce the same failed result,
with the metadata evidence retained separately. No network operation is added.
Search results and direct search-package conversion have no observation.

Collection reasons are `metadata_error_response`, `metadata_collection_failed`,
`metadata_blocked` and `metadata_deadline_exceeded`. Guard rejections use BLOCKED;
other collection failures use FAILED. Existing candidate status, assessment and
error handling are preserved. If identity/configuration is unavailable, no
observation identity is fabricated.

Adapters still raise `RunDeadlineExceeded`. The exception carries
`freshness_observation`, retaining successful metadata if already collected,
otherwise a failed attempt. When the agent catches a fetch deadline with an
observation, it retains a failed, report-only candidate containing that same
observation for the profile result and normal candidate JSON saving. It does not
invent inspection facts or register the candidate for loading. A deadline without
an observation still creates no candidate. The timeout tool error, deadline menu,
budget accounting and loading restrictions are unchanged. Run-level diagnostics
for attempts without an observation remain a subsequent slice.

Freshness tool inputs still contain exactly source, dataset ID and threshold.
The tool now evaluates only properly associated observations using explicit
collector-specific claim selection. Current CBS/CKAN semantics cannot establish
content freshness. Missing or ambiguous matches retain their existing reason
codes without invented observation links. Classifier
evidence, guarded transport, budgets, consent, reassessment, transactional loading
and overwrite refusal are unchanged.

## Offline validation

`tests/unit/test_freshness_observation.py` uses mocked metadata/sample operations
and fixed UTC clocks. It covers full timestamp serialization, presence/type
distinctions, nested immutability, sanitization, key-collision rejection in both
insertion orders at multiple depths, source/resource isolation,
capture-before-sample timing, failures/deadlines, IDs and constructor/summary
compatibility. Existing grounding, tool-argument, budget and loading suites check
the unchanged operational boundaries. A CLI regression follows CBS and CKAN
metadata collection through deadline expiry, the agent timeout handler and saved
candidate JSON, retaining the original observation ID and payload while forbidding
further searches, consent and loading. No live requests or persistence/recovery
guarantees are introduced.
